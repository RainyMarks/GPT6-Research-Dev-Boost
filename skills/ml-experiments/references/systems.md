# 系统与性能实验

适用于操作系统、数据库、分布式系统、网络、存储、编译器、体系结构和 ML 系统等以性能、开销或可扩展性为论断的实验。

## 环境

- 写清硬件（CPU 型号和核数、内存、存储、网卡、GPU）、操作系统和内核版本、编译器和编译选项、依赖库版本、虚拟化方式或云实例类型。
- 控制干扰：固定 CPU 频率或记录频率策略（睿频、节能模式），绑核并留意 NUMA，关掉无关负载。云上实验在不同时间、不同实例上重复，报告波动。

## 测量

- 预热后再计时；冷启动和稳态分开报告。
- 每个配置重复多次，报告中位数和置信区间或分位数。延迟报告 p50、p99 等尾部分位数；吞吐和延迟一起报，画出随负载变化的曲线，一直到饱和。
- 看似无关的实验设置就能让性能结论反转（Mytkowicz et al., ASPLOS 2009, doi:10.1145/1508284.1508275；他们调查的 133 篇 ASPLOS、PACT、PLDI、CGO 论文没有一篇充分考虑这种测量偏差）。提升幅度和噪声相当时，随机化实验设置（多次构建、多台机器、打乱运行顺序）再比较。
- 量出测量工具本身的开销（插桩、采样频率、日志）。

## 负载和基线

- 用领域公认的基准和真实 trace；合成负载写清分布和参数，覆盖从轻载到饱和、从小规模到大规模。
- 基线在同一硬件、同一环境下重新运行，用它推荐的配置并给相近的调优力度，写清版本和配置。加速比相对最强的基线计算，不相对自己未优化的版本。
- 同时报告代价：内存、存储、能耗、额外的代码量或运维复杂度。

## 正确性

优化前后输出一致，用测试或对拍验证。声称一致性、容错或安全性质时，用故障注入、模型检查或形式化证明验证，写明覆盖了哪些故障场景。

## 可复现

一键运行的脚本、环境描述（容器镜像或依赖锁文件）、原始测量数据和画图脚本一起保存。会议有 artifact evaluation 时按它的要求准备。
