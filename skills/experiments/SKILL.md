# 实验

论断—证据表、按独立单元划分、协议对得上论断、同协议对比、多次重复和逐层排查，适用于所有实验。主干的例子多来自机器学习；系统性能、用户研究和各领域的补充见文末。

## 选协议

先写论断—证据表：一条主论断、一两条支撑论断，每条写清能让人信服的结果（数据集、对照、指标、预期幅度）、最强的替代解释和排除它的对照、事先定好的成功标准。每个实验只对应表里的一条，对应不上的不做。方法论文通常需要四类实验：前置实证（证明问题存在、找到成因）、对比（和最强的基线）、消融（核心组件有用）、机制分析（确实通过声称的机制起作用）。具体做法读 `references/protocol.md`。

评测协议要和论断说的场景对得上：

| 论断说的是 | 协议 |
| --- | --- |
| 对同分布的新样本有效 | 按独立单元随机划分 |
| 对没见过的用户、来源、生成器、恶意家族、项目有效 | 按这一级单元留出 |
| 对以后的数据有效（部署、检测新提交、新样本、在线服务；检测器的结果默认属于这一行） | 按时间划分，训练样本全部早于测试样本；测试集的类别比例接近部署场景 |
| 跨数据集、跨环境、跨设备 | 在一个上训练和调参，在另一个上测试 |

主结果用对得上论断的协议。手上的结果来自对不上的协议时（例如论断是部署检测，数字来自随机划分、类别对半的测试集），按对得上的协议补跑一次作为主结果，原结果注明协议后作参考。划分怎么构造、几种约束冲突时怎么取舍，见 `data-gathering`。

## 开跑前

- 数据按独立单元划分，同一单元的样本只出现在一侧（什么算一个单元见 `data-gathering`）。按帧、句子、函数、图块或流随机划分，会把同一单元拆到两边。
- 预处理、归一化、特征选择和数据增强的统计量只在训练集上拟合。
- 选模型、调参、早停和定阈值用验证集；测试集只在最终评估时用一次。
- 基线和本方法用同一数据、同一预处理、同一评测脚本和相近的调参预算。照抄论文里的数字时，注明出处和设置差异。

## 长时间运行

- 启动前先用极小规模跑通一遍（几个 step 或一小部分数据），确认能跑、loss 在下降、日志和 checkpoint 正常写出。新方法先用最小的实验判断值不值得继续，再放大规模。
- 正式训练、批量推理和大规模测量放到后台：日志写文件，定期保存 checkpoint 或中间结果，支持断点续跑。启动后汇报命令、日志位置和预计时长，不在回合里干等。
- 新结果写到新目录，不覆盖、不删除已有的数据集、checkpoint 和实验结果。

## 核查结果

拿到结果、准备写进论文或汇报时逐项过一遍。几分钟能跑完的检查直接跑，结果写进汇报，不列成待办。

- 协议对得上论断吗：对照上面的协议表。对不上就按对得上的协议补跑。
- 有没有泄漏：同一单元是否跨越训练和测试；阈值、超参数、早停是否用了测试集；归一化和特征选择是否在全量数据上拟合。
- 训练数据和测试集有没有重叠（训练数据包括微调数据、检索库、提示词示例）：拼成一份清单，用 `data-gathering` 的 `scripts/check_dataset.py` 先以 `--text` 查规范化后完全相同的样本，再以 `--near` 查改写和近似重复，看它打印的各阈值命中数，阈值选在命中数的断层处并抽查例子。只做完全匹配通常只能查到一小部分。查到重叠时，报告去掉全部重叠样本后的结果，和原结果并列。
- 有没有捷径：和标签相关、和任务无关的属性（数据来源和采集批次、文件格式和长度、文件名或 ID、时间戳、采集设备），用 `check_dataset.py --attr` 测。
- 重复和波动：报告多次运行（多个随机种子、多次重复测量）的均值和标准差或置信区间，不挑最好的一次；差距小时做显著性检验，或写明差异不显著。
- 结果好得反常（准确率接近 100%、远超已发表方法、提速超过硬件上限）时，上面几项全部查完再下结论。

发现问题时，用修正后的协议做一次只读的重新评测：按单元重新划分、在验证集上定阈值、跑几个随机种子、去掉重叠样本。结果写进汇报或新文件，不覆盖原有结果，不改训练脚本的默认行为；汇报里并列修正前后的数字。需要长时间重新训练的，写明问题、影响和重训计划，由用户决定。核查中发现的每个问题都写进汇报，包括和当前要写的数字无关的那些。

负面结果和不及预期的结果如实报告；结果推翻或削弱原论断时，按全局规则写 **换个角度**。

## 结果不如预期时

按全局规则的五层顺序排查，前一层修好、重跑之后再看下一层：

1. 实现：bug、数据管道、预处理、评测脚本；拿一小批样本手算或打印中间结果对照。
2. 配置：超参数、训练预算、是否收敛，和基线的调参预算是否相当。
3. 评测协议：数据划分、指标、阈值，和基线是否同一协议。
4. 机制本身：在可控条件下（小数据、合成数据、去掉干扰因素）它是否起作用。
5. 问题设定：问题本身是否需要重新定义。

几分钟能跑完的修复直接跑；需要长时间训练的，写出计划交给用户。执行失败、比较无效、结果不利是三种情况，分开报告。

## 复现

记录 git commit、配置、随机种子、环境版本、数据版本和运行命令。沿用项目已有的实验记录方式（wandb、TensorBoard、CSV、日志目录），没有的话写进汇报。

## 按实验类型和领域补充

- 实验类型：系统、网络、数据库、编译器、ML 系统等以性能、开销或可扩展性为论断的实验读 `references/systems.md`；用户研究、可用性测试、人工评测模型输出读 `references/human-study.md`。
- 领域：基于学习的安全系统（恶意软件、漏洞、入侵检测、流量分类、欺诈检测）读 `references/security.md`；AIGC 和深度伪造检测、可信取证读 `references/detection.md`；医学影像读 `references/medical.md`；数字水印读 `references/watermark.md`。
- 没有对应文件的领域按主干做，把该领域公认的基准、指标和常见陷阱检索出来写进汇报。数据集本身的采集、划分和体检用 `data-gathering`。
